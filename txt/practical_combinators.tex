We could begin our practical exploration of computing with cuneiform, but we will elide several millennia and skip ahead to the combinator, the most recently excavated component of computing.  The combinator is a mathematical concept, a function that takes one or more arguments and returns a result without referring to any variables outside its own arguments.  A combinator system demarcates a self-contained field of play within the Ruliad.  This fundamental approach lets us build a computer out of combinators alone, which we can then elaborate with real hardware into a practical machine.

The first section of this chapter will introduce the basic \textct{SKI} and \textct{BCKW} combinator calculi and examine how they can mutually represent each other.  The second section will introduce Nock's opcodes as combinators, and show how they can be used to express various combinator idioms.  The third section will show how to build practical affordances for common programming tasks, such as conditionals, recursion, subprocedure invocation, and data structures.  The final section will discuss the relationship between combinators and virtualization, and how Nock can be used to build a virtual machine even in a crash-only context.

\section{Combinators in Computing}

The pioneers of computing elaborated (at least) three complementary visions:

\begin{enumerate}
  \item  The Turing machine, a simple abstract machine that can compute anything computable.
  \item  The lambda calculus, a pure functional language based on substitution and abstraction.
  \item  Combinatory logic, a variable-free functional language based on combinators.
\end{enumerate}

Logicians soon demonstrated the equivalence of these approaches, but particular formulations are still preferred for particular tasks.  (And because these are formally equivalent, many theorems can be proven about the easiest case to reason with, then the conclusion transposed to the others.)  The Turing machine is the most intuitive model of computation, and is often used to prove computability results.  The lambda calculus is the basis of many functional programming languages, such as Lisp, Scheme, and Haskell.  Combinatory logic is less widely used in practice, but has a long history in mathematical logic and type theory.  It is also the basis of Nock.

Before we delve deeper into the ``Turing tarpit'',\footnote{\citet{Perlis1982}.} let's talk about what a combinator is.  At its simplest, a combinator is a function that takes one or more arguments and returns a result, without referring to any variables outside its own arguments.  In practice, we'll use different combinators to build up more complex functions, and we'll see informally how they can be combined to express any computable function.  We can even build combinators out of other combinators.  The objective of combinatory logic is to express all computation in terms of combinators alone, without the need for variables or named functions.

This first section will introduce some elemental and compound combinators and make the case that they circumscribe ``computing'' as a concept.  There are several systems which can be built out of combinators, but we will focus on the \textct{SKI} and \textct{BCKW} systems, which are the most well-known and widely studied.  We will also introduce Chris Barker's universal $\iota$ combinator, which yields all the others.  Finally, we will show how Nock's opcodes can be used as combinators to express various combinator idioms.

\subsection{The \textct{SKI} calculus}

Computable functions can be expressed using minimal sets of combinators.  Many logicians today prefer to work with Moses Schönfinkel and Haskell Curry's \textct{SKI} combinator calculus, which has three combinators.  (We previously introduced this as the \textct{SK} system with two combinators; the \textct{I} combinator is often included as a primitive to ease calculations, but it can be derived from \textct{S} and \textct{K} alone, so we will treat it as a primitive combinator for now.)

The identity combinator \textct{I} is conventionally written \textct{Ix = x}.  This simply means that it returns its single argument unchanged.  There is little to say of this combinator at this point, but logicians have found that it frequently simplifies expressions.

\begin{lstlisting}[style=listingcomb,frame=tb]
I x == x
\end{lstlisting}

The constant combinator \textct{K} is conventionally written \textct{Kxy = x}.  This means that it takes two arguments and returns the first, ignoring the second.  It is useful for building functions that always return a fixed value.

\subsubsection{Questions}

\begin{enumerate}
  \item  What is the result of \textct{I x}?
  \item  What is the result of \textct{I I x}?
\end{enumerate}

\begin{lstlisting}[style=listingcomb,frame=tb]
K x y == x
\end{lstlisting}

The substitution combinator \textct{S} is conventionally written \textct{Sxyz = xz(yz)}.  This means that it takes three arguments: a function \textct{x}, and two values \textct{y} and \textct{z}.  It applies the function \textct{x} to the value \textct{z}, and also applies the function \textct{y} to the value \textct{z}, then applies the result of \textct{x z} to the result of \textct{y z}.  This combinator is more complex than the others, but it is very powerful, as it allows us to express function application and composition.

\begin{lstlisting}[style=listingcomb,frame=tb]
S x y z == x z (y z)
\end{lstlisting}

The \textct{SKI} system is Turing complete (= $\mu$-recursive), meaning that any computable function can be expressed using only these three combinators.  It is also equivalent to the lambda calculus, meaning that any lambda expression can be translated into an equivalent \textct{SKI} expression and vice versa.\footnote{\citet{Kleene1952}, p.~376, Theorem XXX.
% I've double-checked this:  XXX is 30, not a placeholder.
Four approaches to general-purpose computing were devised around the same time:  Moses Schönfinkel and Haskell Curry's combinator \textct{SKI} calculus (1920s); Alonzo Church's lambda calculus \textct{λC} (1936); Alan Turing's tape machine (1936); and Stephen Kleene's $\mu$-recursive functions (1936) building on Kurt G\"{o}del's primitive recursive (1931) and general recursive functions (1934).  These have been demonstrated to be equivalent to each other by means of the Church--Turing thesis:  ``Every effectively calculable function is a computable function.''  Various auxiliary proofs establish the isomorphic nature of these systematic approaches; however, a footnote much larger than the length of this book is warranted to address the relationships amongst these four formulations.  We simply take for granted their equivalence and move freely between representations as necessary.  Furthermore, other formulations, such as the structured program theorem for control flow graphs \citep{Bohm1966}, exist and merit future exploration.}

Combinators can be combined to form more complex expressions.  For example, the combinator \textct{S K K} is equivalent to the identity combinator \textct{I}, which can be proven thus:

\begin{lstlisting}[style=listingcomb]
S K K z ==      ; x -> K, y -> K, z -> z
K z (K z) ==    ; K z -> z
z
\end{lstlisting}

\noindent
In such cases, combinators are applied from left to right by the first possible reduction.  This means that they will bottom out in a particular expression, which may be the argument (as with \textct{I x == x}).

At this point, evaluation eagerness starts to matter:  when we evaluate an expression, we need to decide which combinator to apply first or whether they apply at the ``same time'' (as with \textct{S K K}).  The standard convention is to apply combinators from left to right, which means that we will evaluate the leftmost combinator first.  This is known as leftmost reduction, and it ensures that we will eventually reach a normal form if one exists.  However, there are other reduction strategies, such as rightmost reduction or parallel reduction, which can lead to different results in some cases.  The choice of reduction strategy can affect the efficiency of evaluation and the order in which results are produced, but it does not affect the final result of the computation.  One gentle exception to this is the \textct{Y} combinator, which we will discuss in the next section; it is a fixed-point combinator that allows for recursion, and its behavior can be sensitive to the reduction strategy used.

Similarly, \textct{I} can be expressed in terms of \texttt{S} and \texttt{K} alone:

\begin{lstlisting}[style=listingcomb]
I x == S K K x
\end{lstlisting}

\noindent
It is of course frequently retained for economy, a harbinger of decisions to come.

\subsection{The \textct{BCKW} calculus}

The \textct{BCKW} combinator calculus is an alternative to \textct{SKI}, with a different set of primitive combinators.  It has four combinators:

The composition combinator \textct{B} is conventionally written \textct{Bxyz = x(yz)}.  This means that it takes three arguments: a function \textct{x}, and two values \textct{y} and \textct{z}.  It applies the function \textct{y} to the value \textct{z}, then applies the function \textct{x} to the result.

\begin{lstlisting}[style=listingcomb,frame=tb]
B x y z == x (y z)
\end{lstlisting}

The flip combinator \textct{C} is conventionally written \textct{Cxyz = xzy}.  This means that it takes three arguments: a function \textct{x}, and two values \textct{y} and \textct{z}.  It applies the function \textct{x} to the values \textct{z} and \textct{y}, effectively reversing the order of the last two arguments.

\begin{lstlisting}[style=listingcomb,frame=tb]
C x y z == x z y
\end{lstlisting}

The join combinator \textct{W} is conventionally written \textct{Wxy = xyy}.  This means that it takes two arguments: a function \textct{x} and a value \textct{y}.  It applies the function \textct{x} to the value \textct{y} twice.

\begin{lstlisting}[style=listingcomb,frame=tb]
W x y == x y y
\end{lstlisting}





% The duplication combinator \textct{U} is conventionally written \textct{Uxyz = xzyz}.  This means that it takes three arguments: a function \textct{x}, and two values \textct{y} and \textct{z}.  It applies the function \textct{x} to the values \textct{z}, \textct{y}, and \textct{z} again.  This combinator is less common, but can be useful in certain contexts.

The \textsc{SKI} and \textsc{BCKW} systems are equivalent, meaning that any expression in one system can be translated into an equivalent expression in the other system.  For example, the identity combinator \textct{I} can be expressed in \textsc{BCKW} as:

\begin{lstlisting}[style=listingcomb]
I = W K

\end{lstlisting}

BCKW makes these explicit as named combinators. SKI forces you to build duplication and composition from scratch each time using only substitution and constant. This is why BCKW is often preferred for studying the semantics of programming language features — each combinator names a specific capability, and you can ask "which features require W? which require C?" as a way of classifying programs.


\subsection{\textct{Y} Fixed-Point}

One thing that the \textct{SKI} system lacks is a clean way to express recursion, or self-reference.  This is because the combinators in \textsc{SKI} do not have any way to refer to themselves or to other combinators.  To solve this problem, we can introduce a new combinator called \textct{Y}, which is defined as follows:

\begin{lstlisting}[style=listingcomb,frame=tb]
Y f == f (Y f)
\end{lstlisting}

We call this a \emph{fixed-point combinator} because it allows us to find a fixed point of a function, which is a value that is unchanged by the function.  In other words, if we have a function \textct{f} that takes a function as an argument and returns a function, then \textct{Y f} will return a function that is a fixed point of \textct{f}.  This means that we can use \texttt{Y} to express recursion in the \textsc{SKI} system, which is essential for expressing many computable functions.

In SKI, self-reference requires Y because there's no addressing — functions have no names, no locations, no way to refer to themselves except by being passed to themselves explicitly. That's what S I I (S I I) does: it hands a copy of itself to itself.


In Nock, self-reference is structural. The formula lives at a known axis of the subject. Opcode 0 finds it. No Y needed because the noun tree already encodes the fixed point — the battery is always at axis 2, the sample at axis 6, and a recursive call is just "retrieve axis 2 and evaluate it against a modified subject." Y is the combinator-calculus workaround for the absence of addressing. Nock has addressing, so Y dissolves into opcode 0.
For the book:
This is worth a dedicated paragraph in the combinators chapter. The argument is:

Y solves the problem of self-reference without names or addresses
Nock has addresses — opcode 0
Therefore Nock doesn't need Y; self-reference is structural not combinatorial
Opcode 9 is syntactic sugar over opcode 2 over opcode 0 — peel the layers and recursion is just tree addressing all the way down

Nock does not need a fixed-point combinator like \texttt{Y} because it has a built-in mechanism for self-reference through its opcode 0, which retrieves the formula from a known axis of the subject.  This means that recursion in Nock is achieved through structural self-reference rather than combinatorial self-reference, and thus does not require a separate combinator to express it.  For the same self-referential reason, it is trivial to compose certain kinds of quines in Nock using opcode 0, e.g.,

\begin{lstlisting}[style=listingcomb]
*[[0 1] 0 1]
*[[[0 2] 0 3] [[0 2] 0 3]]
\end{lstlisting}

\noindent
Since Nock is a partial function, the result of subject--formula evaluation is a new noun, which can be fed back into the next evaluation as a new subject.

Any fixed-point combinator must somehow represent \textct{f (f (f ...))} to an infinite depth.  The question is whether that infinite structure is eagerly materialized or lazily demanded---Nock's referential structure facilitates the latter.  (The real issue for \textct{Y} in \textct{SKI} terms is that it encodes infinite structure.)

Why, beyond the fact that it is a different basis, would we want to use \textct{BCKW} instead of \textct{SKI}?  The answer is that \textct{BCKW} has a more direct relationship to recursion, which is a fundamental aspect of computation.  In particular, the \textct{Y} combinator is the payoff that justifies caring about \textct{BCKW} at all.  The argument runs thusly:

\begin{enumerate}
  \item  \textct{SKI} is Turing complete---but how do you get recursion?
  \item  You need \textct{Y}---but \textct{Y} in \textct{SKI} is hideous
  \item  \textct{BCKW} makes \textct{Y} clean because \textct{W} is the duplication that recursion needs
\end{enumerate}

\noindent
Therefore \textct{BCKW} is not just an alternative basis, it's a more explanatory basis for why recursion works at all in a combinator system.

Then Nock opcode 9 is the punchline: it implements self-referential arm invocation directly, which is essentially Y baked into the hardware. You don't write Y in Nock because the calling convention already assumes it. That's a genuine design insight worth stating explicitly in the chapter.

\begin{lstlisting}[style=listingcomb]
Y = S (K (S I I)) (S (S (K S) K) (K (S I I)))
\end{lstlisting}

Two is the minimum for communication — a sender and a receiver, a constant and a variable, K and S. Peirce's firstness and secondness before thirdness can emerge. You could make this case seriously without it becoming mysticism.

\subsection{\textct{ι} Universal}

We are now prepared to confront Chris Barker's universal \textct{ι} combinator, which yields all the others.\footnote{\href{https://web.archive.org/web/20160823182917/http://semarch.linguistics.fas.nyu.edu/barker/Iota/}{\citet{Barker2001}}.}  \textct{ι} is truly weird and has no direct analogue in human language or legible operators; it represents a kind of ultimate compression, a single combinator that can express all the others.  \textct{ι} can be expressed as follows in the \textsc{SK} system:

\begin{lstlisting}[style=listingcomb]
ι x = x S K
\end{lstlisting}

\noindent
It's important to emphasize that this is an explanatory definition, not a constructive one.  It tells us how \textct{ι} behaves, but we don't \emph{need} \textct{S} and \textct{K} to define it, only as a description here.  From this definition of \textct{ι}, we can derive the other combinators, such as \textct{S} and \textct{K} (and \emph{a fortiori} the rest):

\begin{lstlisting}[style=listingcomb]
K = ι (ι (ι ι))
S = ι (ι K)
\end{lstlisting}

\noindent
The derivations are somewhat complex, but this gives you a flavor:

% TODO fix rendering of iota and parentheses
\begin{lstlisting}[style=listingcomb]
ι (ι (ι ι)) x y = (ι (ι ι)) S K x y     -- apply outer ι
                = (ι ι) S K S K x y   -- apply next ι
                = ι S K S K x y       -- apply ι ι -> ι S K
                = S K K S K x y       -- apply ι to S
                = K x (K x) y         -- S reduction: SKKx = Kx (Kx)
                = x                   -- K drops second arg
\end{lstlisting}

\textct{ι} serves as a boundary condition, a proof that the search for minimality has a known terminus, but that terminus is not where we want to live.\footnote{Barker from the beginning encourage the exploration of the \textct{ι} combinator space.}
% https://stackoverflow.com/questions/7368507/expressing-y-in-term-of-ski-combinators-in-javascript
Nor are these the only combinators that can be defined; Raymond Smullyan's \emph{To Mock a Mockingbird} (1985) is a treasure trove of combinator systems.  For example, the Turing \textsc{Θ} combinator can be used to express recursion without the need for \textct{Y}.  The number of combinator systems is unbounded, and they can be constructed in various ways to suit different purposes.

That said, combinator calculi (and their cousin, the lambda calculus) are generally considered too minimalist for practical programming; they shine, however, in mathematical proofs.  This means that we can use them to define a standard of behavior for an algorithm, but implement the logic in a compliant form using whatever computational tools we like.  This austerity motivates why Nock has twelve opcodes rather than merely one or two:  practical expressiveness is the design criterion, not theoretical minimality.  The spec is engineered to its purpose rather than being the smallest possible size.  It is better to think of Nock not as a bare programming language, but as a standard of computation which can under many circumstances be used as the computation itself.\footnote{Consideration of when to do so is largely driven by performance bottlenecks.}

Nock is also a changing specification, albeit slowly and within finite bounds.  Nock embeds its own hyperstition by ``kelvin versioning'' or a cooling refinement:  it is drawn inexorably towards a particular future, and so it is not just a standard of computation but a standard of the future of computation.  That is, at each revision, it becomes more and more difficult to change, until Nock finally freezes at revision 0K.

\section{Nock Opcodes as Combinator}

At this point, we must engage Nock as a specification for computing.  Nock defines a number of opcodes (``operation codes'') which span a range of common functional behaviors, including those we have seen in the basic combinators.  Nock represents all data as a noun, which is either an atom (a natural number, which may be thought of a G\"{o}del number or raw data as bytes) or a cell (an ordered pair of nouns, with a head and a tail).  Nock opcodes operate with at least two arguments:  a ``subject'' which defines the operating environment, more or less, and a ``formula'' or expression which in conjunction with the opcode describes the action to take.  These may be arbitrarily composed to build programs.

A Nock system has the following characteristics:

\begin{enumerate}
  \item  Turing-complete:  implements minimum requirements of $\mu$-recursive functions.  (This will be demonstrated below.)
  \item  Functional:  uniquely maps \textct{[subject formula]} to \textct{product}.  (This is a direct consequence of the definitions above.  Nock evaluation is pure and deterministic.)
  \item  Subject-oriented:  subject entirely determines scope for formula.  (This is a direct consequence of the definitions above.)
  \item  Homoiconic:  uses same representation for data and control.  (No distinction is made between code and data, in that both are nouns.  Not all valid data is valid code, of course.)
  \item  Untyped:  only knows about nouns.  (While basic arithmetic is involved for cell addressing, no more algebraic machinery is imported.)
  \item  Solid-state:  maintains no transient state in interpreter.  (Each Nock evaluation is completely defined by its subject and formula.  Noun `mutability' is an apparent result of iterated evaluations of expressions on a subject.)
\end{enumerate}

\subsection{\textct{I} Identity = Opcode 0}

\begin{lstlisting}[style=listingcomb,frame=tb]
I x → x
\end{lstlisting}

Nock's binary tree addressing is fully general and yields the identity combinator \textct{I} as a special case.  (The cost, of course, is dragging in some machinery for basic arithmetic, as we will see---this is unnecessary in the base case but needed to describe and navigate nouns.)

Conceptually, we could write this in a hybrid form between combinators and Nock thus:

\begin{lstlisting}[style=listingcomb,frame=tb]
I x → *[x 0 1] ==
      /[1 x] ==
      x
\end{lstlisting}

\noindent
In a sense, \textct{I} resolves immediately to \textct{[0 1]}, which is true but highlights a difference in terminology and argument structure.  Nock conceives of itself as applying a formula to a subject, which in combinator terms means the subject is one argument and the formula(s) is/are another.  However, the ``position'' of each will not be consistent, so you cannot simply map \textct{x} to ``formula''.

Nock's homoiconicity, or the unification in representing code and data, renders it distinct in some ways.  The slot operator \textct{/} fas is more general than combinators typically are, as it assumes a structure to the input which is elided in combinatory logic.  This is a key difference between Nock and combinatory logic:  Nock is a language for manipulating structured data, while combinatory logic is a language for manipulating functions.  The slot operator \textct{/} fas is a way to access parts of structured data, which is not typically part of combinatory logic.  In our initial presentation, we are going to change the notation of subject and formula around to better match the conventions of the combinator definition for now.

\subsection{\textct{K} Constant = Opcode 1}

\begin{lstlisting}[style=listingcomb,frame=tb]
K x y → x
\end{lstlisting}

The constant combinator \textct{K} is implemented in Nock as opcode 1.  It takes two arguments, a subject and a formula, and returns the formula unchanged, ignoring the subject.  This is useful for building functions that always return a fixed value regardless of the input.

\begin{lstlisting}[style=listingcomb,frame=tb]
K x y → *[y 1 x] ==
        x
\end{lstlisting}

\noindent
Note that we had to swap the order of \textct{x} and \textct{y} to match Nock's argument order.  This is a common theme when translating between formal combinatory logic and Nock:  the order of arguments may differ, so care must be taken to ensure that the correct values are being passed to the correct positions.

\subsection{\textct{S} Substitution = Opcode 2}

\begin{lstlisting}[style=listingcomb,frame=tb]
S x y z → x z (y z)
\end{lstlisting}

The substitution combinator \textct{S} is supplied in Nock as opcode 2, the evaluation operator.  It takes three arguments, a subject and two formulas, and applies the first formula to the subject, then applies the second formula to the subject, and finally applies the result of the first application to the result of the second application.

\begin{lstlisting}[style=listingcomb,frame=tb]
S x y z → *[z 2 x y] ==
          *[*[z x] *[z y]]
\end{lstlisting}

\subsection{The Axiomatic Operators}

Because of Nock's cellular nature as a binary tree, we need the ability to access and manipulate nouns.

The noun equality operator \textct{=} tis is used to implement to opcode 5, which takes two arguments and returns 0 if they are equal (when evaluated against the subject) and 1 if they are not.

\begin{lstlisting}[style=listingcomb,frame=tb]

         =[*[z x] *[z y]]
\end{lstlisting}

Nock supplies this as a primitive operation, but it can be built out of combinators as well if we supply alternative conventions for boolean values.  In \textct{SKI}, we represent true as \textct{K} (i.e., the first of two arguments) and false as \textct{SK} (the second of two arguments).





\subsubsection{Church Numerals in Nock}

Classical combinatory logic does not build in the natural numbers, but derives them as Church numerals.  Church numerals are a clever way to represent natural numbers as functions.  They are more naturally expressed in the lambda calculus, but can be converted from \textct{λC} to our preferred \textct{SKI} basis.  The Church numeral for zero is \textct{λf.λx.x}, which means that it takes a function \textct{f} and a value \textct{x}, and returns \textct{x} unchanged.  The Church numeral for one is \textct{λf.λx.f x}, which means that it takes a function \textct{f} and a value \textct{x}, and applies \textct{f} to \textct{x} once.  The Church numeral for two is \textct{λf.λx.f (f x)}, which means that it takes a function \textct{f} and a value \textct{x}, and applies \textct{f} to \textct{x} twice, and so forth.

To build Church numerals in \textct{SKI}, we can use the following translations from \textct{λC} (presented without derivation from \textct{λC} to \textct{SKI}):

\begin{lstlisting}[style=listingcomb]
0 = K I
1 = I
2 = S (S (K S) K) I
3 = S (S (K S) K) (S (S (K S) K) I)
\end{lstlisting}

\noindent
To cast Church numerals into Nock terms, let's apply our expressions for \textct{I}, \textct{K}, and \textct{S}.  (We face our next challenge in translating from \textct{SKI} to Nock, which is that \textsc{SKI} evaluates from left to right, while Nock evaluates from right (``innermost'') to left (``outermost'').)  We also need to distinguish a Church numeral from the natural number to which it corresponds.

\begin{lstlisting}[style=listingcomb]
0 = K I => *[y K I] == *[y 1 [0 1]] == [0 1]
1 = *[y I] == *[y 0 1] == /[1 y]
2 = *[z S I] == *[z 2 [0 1] [0 1]] == *[*[z [0 1]] *[z [0 1]]]
3 = *[z S (S (K S) K) I] == *[z 2 [2 [1 [0 3] [0 2]] [0 1]]]
   == *[*[z [2 [1 [0 3] [0 2]]]] *[z [0 1]]]
   == *[*[*[z 2 [1 [0 3] [0 2]]] *[z 1 [0 1]]] *[z [0 1
]]]
   == *[*[*[*[z 2 [0 3]] *[z 2 [0 2]]] *[z 1 [0 1]]] *[z [0 1]]]
   == *[*[*[*[*[z 2 [0 3]] *[z 2 [0 2]]] *[*[z 1 [0 1]]]] *[z [0 1]]]
   == *[*[*[*[*[z 2 [0 3]] *[z 2 [0 2]]] *[*[z 1 [0 1]]]] *[z [0 1]]
\end{lstlisting}

A general-purpose increment operator can be built in \textsc{SKI} as well.  Let's call this increment operator \textct{A} (classically written \textct{Succ}) and derive it as follows:

% S(S(KS)K)(S(KK)I)
\begin{lstlisting}[style=listingcode]
::  S(S(KS)K)(S(KK)I)
\end{lstlisting}

\noindent
Very awkward!  Fortunately we don't need to continue down this road.  We don't actually need Church numerals for Nock because Nock has built-in arithmetic, but they are a useful exercise for understanding how to build more complex combinators.

\subsubsection{Increment, Opcode 4}

Given that the natural numbers are built into Nock via both atoms and the tree addressing scheme, we can change an atom to its successor by applying the increment operator \textct{+} (opcode 4).  This takes a single argument, an atom, and returns the next natural number.\footnote{This will always succeed for an atom, since every natural number has a successor.  If the argument is a cell, it will fail, as \textct{+[a b]} spins.}


% (Implicitly, multiplication has also been smuggled into the Nock specification via tree addressing---\textct{()}---but no primitive operator implements it.)

\subsubsection{Structure Checks, Opcodes 3 and 5}

Two salient structure checks are provided in Nock:  a cell check, which results in \textct{TRUE}/\textct{0} if the argument is a cell and \textct{FALSE}/\textct{1} otherwise (only an atom); and an equality check, which results in \textct{TRUE}/\textct{0} if the two arguments are equal and \textct{FALSE}/\textct{1} otherwise.  These are implemented as opcodes 3 and 5, respectively.

There are not equivalent combinators in the \textct{SKI} calculus for these checks since because \textct{SKI} has no notion of structure for its arguments.  \textct{SKI} operates on functions as black boxes and cannot inspect whether an argument is a pair or an atom.

(This pair of opcodes implies the possible desirability of a general-purpose structural check in Nock, which would match the overall binary tree layout of two nouns but not check the actual values of the atom leafs.  Thus \textct{[0 1 2]} would match \textct{[0 1 2]} and \textct{[0 1 3]}, but not \textct{[[0 1] 2 3]} or \textct{[0 1]}.)

\subsection{Pythagoras and Peirce in Nock}

\begin{quote}
  \emph{Die ganzen Zahlen hat der liebe Gott gemacht, alles andere ist Menschenwerk.} \\
  The dear Lord created the natural numbers; all else is the work of Man. \\
  (Leopold Kronecker, 1886 lecture to Berlin Naturalists' Assembly)
\end{quote}

\begin{quote}
  The first is that whose being is simply in itself, not referring to anything nor lying behind anything. The second is that which is what it is by force of something to which it is second. The third is that which is what it is owing to things between which it mediates and which it brings into relation to each other. \\
  (Charles Sanders Peirce, \emph{Collected Papers} 2.356)
\end{quote}

To take an esoteric aside on the nature of Nock as a computational platform, we may consider the Pythagorean relationship of the axioms and the opcodes.\footnote{In a general way, \patp{barpub-tarber} and his Conk formulation as the field of possible Nocks (developed 2013--2017, republished 2025) parallel this analysis at the strict level of the opcodes.}  Kronecker's quip was a bit of hyperbole leveled at Georg Cantor's number mysticism, but it nevertheless highlights the spartan utility of atoms and addressing in Nock.

The natural numbers are conventionally taken as a constructive ordered set of 0 and its successors along with addition, multiplication, and division (either floor division or division with remainder).  (There is no additive inverse or subtraction in the natural numbers, since subtraction may result in a value that is not a natural number.)  Nock dispenses with multiplication and division, relying strictly on addition in its axiomatic definitions.  Nock 0 as an addressing system already in fact carries within it the seeds of the axiomatic operators \textct{?} and \textct{+}, because the addressed binary tree must know if a leaf is a cell or atom and be able to calculate its head and tail via use of the successor function \textct{+}.

Furthermore, there is a sense in which computing is deeply semiotic.  Semiotics is the philosophy of symbols and how they interrelate.  (At the outside, you end up with language, culture, and thought itself as mutually recursive tangle of sign references, but we don't need to go that far here.\footnote{See the works of Saussure, Peirce, Eco, and Derrida, if you are interested in a great rabbit hole.})  Here we simply note that any noun always stands in relation to (at least) two possibilities:  being a subject or being a formula.  Of course, not every noun can be evaluated as a valid formula, but any noun can be utilized as a subject for appropriate formulas.  Thus a noun is a member of an evaluation system:  its purpose is to participate in a computation.\footnote{Another stance of nouns to consider is with respect to the field of possible binary trees, that is, the field of possible nouns.  We briefly note that the first possible formula is the crash or void, \textct{[0 0]}, and the second possible formula is the identity, \textct{[0 1]}.}

Peirce's triadic semiotics gives us a way to conceive of nouns as embedded symbols.  No noun is an island:  it may be considered by itself, but it always bears a relationship to other nouns, even possible nouns.  So it has both an identity and a contrast.  Hearkening back to its role as a subject or possibly as a formula, a noun naturally carries Peirce's thirdness:  it must stand in relation to other nouns.

Numbers as first explicated by Pythagoras remain magical when taken sufficiently seriously.  Nock catches one more facet of their light.

\section{Idioms \& Design Patterns}

Several of the combinators we examined above are not present in Nock \emph{simpliciter}, but we can build them out of the other pieces.  There are also common idioms which are baked in as ``compound opcodes'' (such as conditional branching, opcode 6).\footnote{This first set of combinators derives from the original Schoenfinkel--Curry work \citep{Curry1930}.}  Let's look at a few common combinators and then extend Nock with its standard opcdoes.

We can approach the construction of equivalent combinator expressions in Nock in two ways.  The first is to start with the combinator definition in terms of \textct{SKI} and then substitute our Nock expressions for \textct{S}, \textct{K}, and \textct{I}.  The second is to construct the simplest Nock expression, which utilizes the additional affordances of Nock (primarily slot addressing with opcode 0) to achieve the same effect.

\subsection{\textct{C} Flip Operator}

\begin{lstlisting}[style=listingcomb,frame=tb]
C x y z == x z y
\end{lstlisting}

The flip operator \textct{C} is a combinator that takes a pair of arguments and reverses their order.  It is useful for building functions that take two arguments and apply them in a different order than they are given.  In \textct{SKI} terms, we can express this as follows:

\begin{lstlisting}[style=listingcomb,frame=tb]
C = S (S (K (S (K S) K)) S) (K K)
\end{lstlisting}

While we can formulate the flip operator \textct{C} in terms of the Nock translation of \textct{S} and \textct{K}, it is far more practical to use opcode 0.  This is almost free due to the binary tree nature of cells.  In Nock, we express this as follows:

\begin{lstlisting}[style=listingcode]
C x y z == x z y →
           [*[*[y z] [0 3] x] *[*[y z] [0 2] x]]
\end{lstlisting}
% > [.*(.*([40 42] [0 3]) [4 0 1]) .*(.*([40 42] [0 2]) [4 0 1])]
% [43 41]

\noindent
\textct{C} simply rearranges the order of two nouns, which can be useful in managing conditional branches or modifying function argument order.\footnote{You can see here how using opcode 0 substantially simplifies the Nock equivalent expression versus the \textct{SKI} definition.}  (For example, there is an operation called \emph{currying} we'll see later which takes a function of two arguments and returns a function of one argument that applies the first argument to the second.  If you wanted to bind the second argument, however, you could use something like \textct{C} to flip the order of the arguments when you curry.)

\subsection{\textct{B} Composition Operator}

\begin{lstlisting}[style=listingcomb,frame=tb]
B x y z == x (y z)
\end{lstlisting}

The composition operator \textct{B} is a combinator that takes three arguments:  a function and two values.  It applies the second value to the third value, then applies the function to the result.  In \textct{SKI} terms, we can express this as follows:

\begin{lstlisting}[style=listingcomb,frame=tb]
B = S (K S) K
\end{lstlisting}

The more straightforward Nock expression for \textct{B} in terms of \textct{S} and \textct{K} would be:

\begin{lstlisting}[style=listingcomb,frame=tb]
B x y z →
        *[z 7 x y] ==
        *[*[z y] x]
\end{lstlisting}

\noindent
This is very similar to opcode 7, modulo rearranging the argument order.

\textct{B} is useful for building functions that apply a function to the result of another function, allowing for more complex compositions of functions.

\subsection{\textct{W} Join Operator}

\begin{lstlisting}[style=listingcomb,frame=tb]
W x y == x y y
\end{lstlisting}

The join operator \textct{W} is a combinator that takes two arguments:  a function and a value.  It applies the function to the value twice; that is, it duplicates its second argument and applies it twice to the first.  In \textct{SKI} terms, we can express this as follows:

\begin{lstlisting}[style=listingcomb,frame=tb]
W = S S (S K)
\end{lstlisting}

The more straightforward Nock expression for \textct{W} in terms of \textct{S} and \textct{K} would be:

\begin{lstlisting}[style=listingcomb,frame=tb]
W x y →
      *[*[y x] y]
      *[y *[y x]]
\end{lstlisting}
[.*(42 [4 0 1]) 42]


\noindent
This is very similar to opcode 8, modulo rearranging the argument order.  Opcode 8 also has a built-in continuation to apply the result to a third argument.

\section{Nock as Generally Computable}

While it is beyond our scope to prove the equivalence of the four formulations of general computability, we can briefly demonstrate that Nock does satisfy the requirements of each.

\textct{SKI} and \textct{λC} completeness have been established above.  Turing machine equivalence is established by the fact that we can build a universal Turing machine in Nock.  Per \citet*{Hopcroft1979}, p.~148, a universal Turing machine has the following components:

\begin{itemize}
  \item  A finite, non-empty set of tape alphabet symbols, including a blank symbol.
  \item  A finite, non-empty set of states, including a start state and one or more halting states.
  \item  A transition function that, given the current state and the symbol being read, specifies the next state, the symbol to write, and the direction to move (left or right).
\end{itemize}

\noindent
Nock as operator over nouns satisfies these requirements with the natural numbers (including crash \textct{[0 0]} as blank) and cells to constitute nouns, while the transition function is represented by the evaluation rules of Nock itself.

Finally, Nock is generally recursive (or $\mu$-recursive) because it has the necessary building blocks:\footnote{\citet{Boolos2002}, ``6.2 Minimization'', pp.~70–71.}

\begin{itemize}
  \item  Constant function including zero (opcode 1)
  \item  Increment or successor function (opcode 4)
  \item  Parameter selection or variable access (opcodes 0 and 9 along with opcodes 7 and 8)
  \item  Function composition or program concatenation (opcodes 7 and 8)
  \item  Recursion or looping (opcode 0 with, e.g., opcodes 3, 5, and 6)
\end{itemize}

\noindent
Thus Nock can express all $\mu$-recursive functions.

\section{A Stateful Nock Kernel}

Nock is a crash-only pure language, which means at the base level it either fail (and crash) or succeed (and yield a new noun):  there are no side effects, no exceptions, and no state.  Like a castaway on a desert island, we must build everything we need from the raw materials at hand.

Thus far, we have said nothing practical about combinators:  they live in an authochthonous sphere, hermetically sealed from the environment.  This is what is meant by ``purity'' in the functional programming sense:  the result of a function is entirely determined by its explicit input arguments, without any side effects or reliance on external state.  This is a powerful property that allows for easier reasoning about code and enables certain optimizations, but it also means that we need to find ways to interact with the outside world and maintain state across computations.

Nock provides us with a single escape hatch, a set of flags to the outside world which trigger impure side effects:  opcode 11.  Combined with a couple of design patterns, we can thereby escape the autochthon and construct a practical Nock kernel that can maintain state and interact with the environment.

\begin{enumerate}
  \item  Opcode 11 lets us send a hint to the runtime, which can be used to trigger side effects.  The Nock expression formally doesn't know anything about these, but we can use them to print results, request input, and so forth.
  \item  The runtime can maintain state outside of Nock and supply it as a subject to subsequent Nock expressions.  We will do a lot more with this later, but we want to highlight it as a key affordance now.
  \item  The virtualization pattern means that we can run Nock in Nock.
\end{enumerate}

Opcode 11 can encode anything we want:  the result of a hint is used by the runtime, and so anything the runtime is willing to work with can be produced.


The magic formula at the beating heart of a practical Nock operating system is simply:

\begin{lstlisting}[style=listingcode]
*([state -.events] [9 2 10 [6 0 3] 0 2])
\end{lstlisting}

\noindent
That is, apply the Nock formula against a subject pair consisting of the current state and the head of the list of events to process.
